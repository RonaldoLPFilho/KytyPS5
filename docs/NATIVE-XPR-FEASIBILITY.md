# 原生 XPR draw 可行性研究（2026-09-25）

目标：让 XPR 的每个 draw 在主机上只剩"推一个记录序号 + 记录一次间接 draw"，把 XPR draw 的约 9.3 ms 渲染 CPU
（路线 B 模式 9 实测）尽量拿回来，同时画面正确。

## 1. 深度通道：完全可行

| 项 | 内容 | 来源 |
|---|---|---|
| 着色器 | VS `7833ddbaf675c1c3`（另有 `daa84716d49bf71d`）+ PS `0a206f666bd26c5f`（无资源，只写深度） | ds_pc 导出计划 |
| user data | `s8:s9` = 几何根 R，`s10` & 0xffff = 实例偏置 | ds_decompile T5，ds_pc |
| 常量（32 dword） | `*(R+16)`、`*(R+0)` 得三个指针 A/B/C；`A+16`、`B+16` 各 4 dword 为两个缓冲描述符；`C+192` 16 dword 为投影四行，`C+448` 2 dword 为裁剪偏移 | fixed-readers.json |
| 缓冲 | 实例变换（每实例 3 行 vec4，步长可变）、位置（vec3，带格式） | ds_pc `pbr_depth.vert` |
| 语义 | `clip = proj × (inst × pos)`，再加裁剪偏移；ds_pc 手写替代着色器已做过像素级对照 | ds_pc NATIVE-DEPTH |

深度通道每帧约 3,470 个 draw，但普通路径只花约 2.6 ms（模式 7），单做它最多 +1.7 FPS。它的价值是当试点。

## 2. 其他通道：结构一致，但着色器种类多

- GBuffer 对 `f4d2e78cd1769fc7`/`a254ad5aa4a3b90a`：VS 5 个缓冲、59 dword 常量；PS 3 张图、2 个采样器、40 dword 常量。
  全部资源都经 R 的固定读链得到（ds_pc fixed-readers），没有运行期分支寻址。
- 本次会话日志里出现的 XPR VS 已超过 10 种，ds_pc 统计 PBR 共 222 个着色器对。**手写替代着色器不可行，必须让着色器翻译器自动生成。**

## 3. 翻译器现状（决定改动量）

- 缓冲：已经是存储缓冲数组；**带格式（texel）读取在着色器内解码**（`LoadWideBuffer`/`PrepareFormattedMemory`），格式由程序特化决定，
  同一 permutation 的对象格式一致。→ 改成"从每对象记录取设备地址 + 记录数"是局部改动（地址计算、越界判断两处）。
- flattened SRT：以常量偏移从一个存储缓冲读。→ 加一个"每 draw 基偏移"（push constant）即可。
- shader data（user data 寄存器、对齐偏移、LOD 统计）：push data 或存储缓冲。→ 并入每对象记录或每 draw push。
- 图像/采样器：按绑定类别的定长数组。→ 改为描述符索引的大数组，下标 = 记录中的槽号（每 draw 内一致，无需 nonuniform）。
- 已有 `PhysicalStorageBufferAddresses` 能力与 BDA 页表路径，可复用类型与能力声明。

## 4. 运行时设计

1. **每对象记录**（键 = 程序 permutation + user data）：由普通路径首次翻译时的求值结果生成——常量、各缓冲设备地址与记录数、
   图像/采样器在大数组中的槽号、shader data。记录存 GPU 缓冲，按对象复用。
2. **每帧维护，而非每 draw**：
   - 常量：复查 SRT 读取的字；已学会的"纯数据字"（如每帧时间常量）直接补丁（路线 A 已实现并校验）。
   - 缓冲：CPU 改写过的范围先同步，若落到上传环/缓冲换了，则更新记录中的地址。
   - 图像：每帧每图刷新一次内容（已实现），槽号只在图像换代时重写。
3. **每 draw**：推送记录序号，`vkCmdDrawIndexedIndirect` 直接读剔除输出（已实现并验证画面正确），索引池每批绑定一次（已实现）。
4. **管线**：原生模式用自己的 pipeline layout（记录缓冲 + 图像/采样器大数组），与普通管线并存；每个链/材质组绑定一次。
   链头（寄存器真实变化的 draw，约 1,340/帧）仍走普通路径并负责生成/刷新记录。

## 5. 收益估算

- 上限：XPR draw 全部去掉 = 33.1 FPS（模式 9）。
- 剩余成本：每 draw 约 0.15 µs × 约 5,300 ≈ 0.8 ms；每帧对象/图像维护约 1～1.5 ms；链头仍是普通路径。
- 预计 **约 30～32 FPS**；再做原生剔除（另约 5 ms 上限）约 34～36 FPS。GPU 每帧约 19 ms，不构成限制。

## 6. 工作量与风险

| 部分 | 估计 |
|---|---|
| 翻译器"每对象表"模式（常量基偏移、缓冲走设备地址含越界、图像/采样器大数组、shader data） | 1～2 周 |
| 管线布局变体与管线缓存接入 | 3～5 天 |
| 运行时：记录表、描述符大数组管理、每帧维护、命令处理器批次控制 | 1～2 周 |
| 校验：记录与普通路径求值逐项对照、截图、长时间游玩 | 约 1 周 |
| **合计** | **约 4～6 周** |

风险：个别 XPR 着色器带写入/原子/GDS/DMA（需回退普通路径）；CPU 每帧改写的小缓冲导致记录地址每帧变；
链头比例若比估计高，收益相应下降；纹理流送与对象卸载的失效要完整覆盖（已有的 `XprGeometryDestroy` 等逆向结论可作为额外保险）。

## 7. 建议的第一步

用深度 VS `7833dd…` 做翻译器新模式的端到端试点（只有常量和两个缓冲，没有图像）：
翻译器生成"每对象表"版本 → 运行时建记录 → 深度通道按新路径绘制 → 与普通路径逐像素对照深度。
约 1 周；通过后再扩到图像/采样器（GBuffer）与阴影。
