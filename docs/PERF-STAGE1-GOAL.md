# 阶段 1：已完成数据的回读不再排在图形队列尾部（2026-09-27）

用户要求：在阶段 1 上继续，常态超过 35 FPS；不做针对场景的参数调优，只做逻辑上通用的优化。
分支 `experiment/perf-40fps-20260926`（worktree `_Build/hist/src`），只在本地提交，不推送。

## 先追踪，确认帧首链卡在哪

把追踪工具移植到当前代码（038d79a、642c408、a768b38）：live `trace` / `tracew` / `tracem`，
分析脚本 `tools/local/live-trace.py`（`frames`、`frame`、`gpu`、`producers`、`marks`，内存有上限）。

- 异步客体回读：3 秒内 5580 次，其中 4646 次（83%）读的数据在请求时 GPU 早已写完，
  但拷贝被追加到唯一的图形队列末尾，要等前面所有工作（1～5 ms）。帧首读"三帧前数据"的回读
  （0x3cXX…、0x3aXX… 三缓冲环）等的是上一帧 GPU 尾巴，剔除提交被它卡住。
- 渲染线程自己的同步下载（`DownloadBufferMemory` → `Finish()`，约 4.5 次/帧，读间接参数等）
  在图形队列翻译窗口里等 GPU 约 1.0～1.2 ms/帧，读的同样是早已写完的数据。
- 翻译窗口里渲染线程已无空闲（主提交后 render idle = 0），此处节省的时间约 1:1 变成帧时间。

## 实现：`KYTY_READBACK_QUEUE`（默认关）

- 设备多建一个只做传输的队列（拷贝引擎，NVIDIA 队列族 1）；缓冲改为 `VK_SHARING_MODE_CONCURRENT`（两个队列族共享）。
- 缓冲缓存记录可能仍在执行的 GPU 写（着色器写、上传、图像→缓冲拷贝、缓冲合并）；
  写入的 tick 只在命令之间（客体回读处）确定，命令内部未确定的写一律视为"还在当前命令缓冲"。
- 客体回读与同步下载：读到的字节若没有未完成的 GPU 写，就在传输队列拷贝，只等图形时间线到"已完成"值；
  否则走原路径。模式 2（只等最后写入者）实测无额外收益。
- 模式 3（校验）：每次同时在图形队列再拷一遍并逐字节比较，使用图形队列的字节，计数 `rb_queue_verified` / `rb_queue_mismatch`。
  校验发现一个真实问题并已修复（b02d6cb）：回读槽的下载缓冲可能还有被分离请求的图形队列拷贝在排队，
  会覆盖拷贝引擎写入的结果（约每 2 秒一次，客体会读到别的窗口的字节）。修复后拷贝引擎还要等该槽上一次图形队列拷贝。

提交：0de8dbc（客体回读）、1715829（同步下载）、b02d6cb（槽顺序修复 + 模式 3 + 缓冲合并/上传/图像拷贝入日志）。

## 结果

- 同进程 A/B（官方场景，5 轮 × 8 秒，七个阶段 3 开关全开）：
  - 修复前：模式 0 → 1：35.00 → 36.62 FPS（+1.62，每轮都涨）
  - 修复后：模式 0 → 1：34.80 → 36.05 FPS（+1.25，配对中位 +1.37，每轮都涨）
- 追踪（模式 1）：帧 26.95 ms（追踪中）= 帧首链 8.2 ms（GPU 受限：上一帧 GPU 尾巴 6.4 ms + 剔除）
  + 翻译窗口 18.8 ms（渲染线程 100% 忙）。同步下载 1.19 → 0.29 ms/帧，GPU 等待 1.05 → 0 ms/帧。
- 校验：官方场景约 42 万次比较 0 不一致。

## 剩下的限制与可能方向

- 帧首链现在由 GPU 执行时间决定：上一帧最后约 20 个全屏计算后处理 pass（每个 0.1～0.6 ms，共约 6.4 ms），
  其后是下一帧剔除。剔除等待的标签由新一帧 q0 的 WRITE_DATA 写出，而这段 q0 在 q0 自身顺序里排在上一帧尾巴之后，
  再加上中间的部分刷新（全屏障），单独开异步计算队列也仍要等尾巴，所以这不是异步队列能单独解决的。
  继续缩短需要 GPU 端（着色器代码生成）优化。
- 翻译窗口：渲染线程 CPU（XPR 剔除 dispatch 约 3500 次/帧 6.2 ms、原生 XPR 5.5 ms、普通 draw 4.1 ms），节省约 1:1 转成帧时间。
