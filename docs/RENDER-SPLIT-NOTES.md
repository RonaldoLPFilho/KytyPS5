**注意（2026-09-26 补）**：本阶段所有测量都带着原生 XPR 的渲染错误（普通 draw 后原生 draw 沿用其管线/索引缓冲，见
`docs/PERF-40FPS-GOAL.md` 同日条目；修复 `a5d2314`）。错误时轻时重，会让 GPU 少做工作；恢复拆分前先在修复后的代码上重测基线与拆分 A/B。

## 结论先说

1. **拆分骨架可用且正确**：前端线程（Kyty.Front）接管调度与 PM4 遍历，后端（Kyty.Gpu）按前端的切片与停止位置执行；
   运行时开关可来回切换；后端停止位置与前端 0 不一致、0 排空；截图正常。
2. **前端预计算（dispatch 程序+SRT、draw 程序+SRT）校验通过**：0 个无法解释的不一致；所有差异都是
   "客体在前端读取后又改写了每帧常量块"的竞态（前端读到的更接近提交时刻，反而更接近主机行为）。
3. **但拆分没有带来帧率**：同进程 A/B 基本持平（31.1～31.5 vs 30.9～31.4，-O2 构建）。
   后端 CPU 每帧只省约 1～1.8 ms（搬走了约 5 ms 的查找），且后端处理窗口的墙钟时间完全没变（27.56 vs 27.57 ms，带追踪）。
4. **根本原因是帧的关键路径结构**，不只是渲染线程 CPU：见下节。按现有数据，单靠拆分到 40 FPS 很难。

## 帧的关键路径模型（官方场景，已测）

一帧（从后端消费上一帧边界算起）= 链 + 后端翻译窗口：

```
边界 ──► GPU 尾巴(上一帧末尾重 GPU 通道，约 3.6～5 ms) ──► 下一帧剔除(GPU) + 客体回读链 ──► 客体提交主命令(约 7.4 ms)
     ──► 后端翻译整帧(-O2 约 24.3 ms；PGO 约 21 ms；此段 GPU 大多空闲 10～50%) ──► 边界
```

- PGO 下约 29 ms ≈ 后端 CPU 密集段 15.8 + GPU 重尾段 10 + 链 3.3（模型与实测 34.5 FPS 吻合）。
- 1 ms 桶时间线：后端在主提交后 100% 忙而 GPU 只有 10～50%；帧末约 10 ms GPU 连续 95% 忙（光照/后处理等），
  跨过边界约 4 ms；此期间后端空闲（等客体）。
- 游戏的依赖是真实的：下一帧剔除计算（q9/q49 等）等待"本帧完成"标签（`0x24175da90` 帧计数），
  客体读剔除结果后才提交下一帧主命令；单个 Vulkan 队列上剔除只能排在本帧 GPU 尾巴之后。
- 加延时实验：后端每帧 +1.82 ms CPU → 帧 +1.28 ms（敏感度约 0.7）。
- 模拟：后端窗口按比例压缩 f=0.85 → 窗口+尾巴 -3 ms；f=0.8 → -4 ms（尾巴每 10% 只长约 0.5 ms）。
- GPU 每帧执行约 16.3 ms（时间戳）、空闲约 15.9 ms；利用率约 53%。

## 为什么拆分没变快（已测到的原因）

- **交接开销吃掉大部分收益**：每个 draw/dispatch 的工作只有 1～5 µs，跨核交接（缓存行迁移、拷贝 vs/ps 输入信息、
  swap dispatch 输入）每项约 0.3～1 µs。后端 dispatch 的非程序阶段反而变慢约 0.6 ms（special/prepare/bda）。
- **程序缓存互斥锁争用**：前端准备时几乎一直持锁，后端回退路径（被污染的 draw 约 30%、原生 XPR、draw run）拿锁要睡眠，
  约 1.5 ms/帧；改自旋锁后等待变短但 FPS 仍不变。
- **污染**：约 320 次/帧准备因读到 GPU 监视页而作废，后端自己再算。
- **帧中客体回读变慢**：后端变快后 GPU 队列更深，客体每次回读（每帧一条约 40 次的串行回读链）从约 0.06 ms 变成 0.17～0.9 ms，
  客体第三批提交从约 18.5 ms 推迟到 23.7～28 ms。移植回"反馈预取"（`KYTY_FEEDBACK_PREFETCH`，每帧约 60 次命中）后这段恢复正常。
- **帧首链变长**：后端更早结束 → 本帧 GPU 尾巴更晚结束（+1.44 ms）→ 下一帧主提交 +0.5 ms，抵消收益。
- 可能还有：多一个忙碌 P 核导致睿频下降（未测）；前端线程与客体共享 CPU（前端在 7 号核，客体工作核 1～23 除 4、5）。

## 做了什么（代码在 WIP 分支，开关都默认关）

- `KYTY_RENDER_SPLIT`（0～3，可运行时 `sym kyty_local_render_split_mode N` 切换）：
  1 仅拆分；2 + 前端准备 dispatch/draw 程序与 SRT；3 + 校验（后端重算并比较，差异分"竞态/逻辑"两类计数）。
  - `src/local/render-split.h`：PM4 位置、待写覆盖层（前端遍历过但后端未执行的写：WRITE_DATA/EOP/DMA/常量 RAM/遮挡查询等，
    精确值或"未知"），`FrontReads`（前端安全读：覆盖层、GPU 监视页 → 污染）。
  - `src/local/render-split-prepare.h`：按计数匹配的准备环（dispatch/draw 包序号）。
  - `graphicsRun.cpp`：`EnterSplit`/`RunBackEnd`/`ExecuteSplitItem`/`FrontThreadRun`/`FrontProcess`/`FrontWalk`，
    前端每准备 32 个单元（后端等待时每 1 个）交出一段（后端停止位置不落在 draw 连续包中间），后端短自旋后才睡眠。
  - CommandProcessor 前端模式：所有 draw/dispatch/宿主工作跳过，内存写入覆盖层，等待/谓词/COND_EXEC/分支/间接寄存器表按覆盖层读，
    读到未知待写则挂起并等后端追上（"排空"）。
- 程序缓存锁拆分：`m_program_mutex`（程序/SRT 状态）与 `m_mutex`（管线表）分开，前者改为自旋锁。
- `KYTY_EPOCH_RELAX`：下一帧计算提交可越过当前帧边界（结论：游戏用标签自己同步，无收益）。
- `KYTY_FEEDBACK_PREFETCH`：从 4134ca6 移植回反馈预取（学习热页、每帧首次图形切片时不等待快照、客体读优先用快照）。
- 诊断：`live-trace.h` + `trace/tracem` 命令（调度事件时间线、每命令缓冲 GPU 时间戳、每 draw/dispatch GPU 时间戳）、
  `vkcalls`（每帧 Vulkan 调用次数与屏障/拷贝调用点）、`proff/profwf`（前端线程采样）、若干计数器（空闲/等待拆分、冗余全屏障等）。
  实验开关：`kyty_local_global_barrier_mode`（1 去冗余全屏障，9 全部跳过——只用于测量）、`kyty_local_back_delay_ns`。
- 工具（本地，未入库）：`tools/local/live-trace-report.py`；`perf40-stage.py` 改为以 33 FPS 组合为基线；
  `play-demons-souls.py` 开关白名单补上新开关（**修复了 33 FPS 包的启动检查**）。

## 其他实测数据

- 每帧 Vulkan 命令：约 3,760 次管线屏障（Image::Transit 约 950、EmitGlobalBarrier 约 920（其中约 330 次前后无任何命令）、
  上传前后约 610+610、写冒险约 370），BeginRendering/EndRendering 各 716，BindPipeline 6,292。
  跳过全部全屏障（仅测量）FPS 不变；去掉冗余的 +0.3（噪声级）。
- 最重的 GPU 命令缓冲：同一个计算着色器 `0x208ac7300` 的 128 次 dispatch 批（每批 1.7～2.5 ms），
  以及约 450 个小 draw 的批（6 个着色器各 40～56 次，1.6～2.0 ms）→ 更像单次 draw/dispatch 的 GPU 固定开销而非着色本身。
- wave64 计算着色器在 NVIDIA（子组 32）上由一个宿主线程模拟两条 guest lane（`lane_count = 2`），可能降低占用率（未量化）。
- 像素着色器的 LOD 统计插桩：每次采样都有 `OpImageQueryLod`（在使能分支之外），原子操作只在使能时执行（未量化）。

## 若恢复，建议的方向（按预期收益）

1. **帧首链 + GPU 尾巴（最大杠杆，约 4～5 ms）**：让下一帧剔除与其回读不排在本帧 GPU 尾巴之后
   （第二个 Vulkan 队列 + 按资源的读写 tick 依赖，而不是按"帧完成"标签）。先测：剔除 dispatch 的输入最后写 tick、
   输出最后读 tick 与本帧尾巴的关系；若无冲突再实现。风险高（跨队列同步、图像布局）。
2. **GPU 批的固定开销**：上面两类重命令缓冲（128 次同 shader dispatch、450 个小 draw）；看屏障/管线切换/描述符以外的开销。
3. **拆分效率**：前端固定到空闲 P 核（4/5 号），更粗粒度交接，减少污染，原生 XPR 也拆；测睿频影响。
   预期单独收益 ≤ 1～2 ms。
